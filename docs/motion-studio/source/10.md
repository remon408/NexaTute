# 10. Technology Architecture, AI Models and GPU Capacity

This chapter is the technical design of Motion Studio for the developers who will build it and for the board and investors who need to judge its risk. Motion Studio runs on the shared RemonLogic ecosystem platform (servers, Kubernetes cluster, databases, storage, safety models and admin panel) but keeps its own product identity, APIs, queues, data, billing and failure behaviour from the first request to the last byte delivered.

> All capacity and speed figures in this chapter are planning estimates. They are replaced by measured results from the GPU test and launch benchmark before any capacity or delivery promise is published.

## 10.1 Architecture principles

1. Browser first. Everything a normal device can do runs in the creator's browser (Quick-mode render, 2.5D motion, captions, audio mix, MP4 assembly). The servers keep only large AI models, work that needs secret keys, results that must be trusted (money, safety, Content Credentials), work that must continue after the tab closes, and the fallback for weak devices.
2. Cheapest suitable path per scene. The AI Director routes each scene to the cheapest path that meets the quality asked for; only hero shots use full video generation.
3. One shared ecosystem, strict product isolation. GPUs and CPUs are shared through one scheduler with owner-first priority; APIs, queues, caches, databases, credentials and billing are never shared.
4. Durable state first. Every job, charge, refund and retry is tied to one job record and idempotency key in PostgreSQL before any GPU work starts.
5. Free, open-source, commercially usable software and model weights only, with every licence recorded and checked in CI (10.12). Deliberate exceptions are listed.
6. Measured, not assumed. GPU-minutes per output minute, quality thresholds and capacity come from benchmarks and live metrics.

## 10.3 Video pipeline

The pipeline below is the canonical order of work for one order. Each numbered step is a durable state change.

1. Request. The creator submits a brief, uploads a script or source video, or orders by WhatsApp voice note or link. The API checks identity, content plan (General or Islamic), package entitlements from the "Packages & features" matrix and the live package settings.
2. Job record. A job record and idempotency key are written first, so every later charge, retry and refund belongs to one job.
3. Intake and rights. Uploaded files go straight to R2; the Document Intake Service parses scripts (including Bijoy-to-Unicode conversion) and images; source videos pass the ownership declaration, connected-channel check and Chromaprint fingerprint check before any processing.
4. Safety before generation. Prompts, scripts and uploads pass the text, audio and image safety layers; blocked or flagged items never reach the GPU queue (chapter 12).
5. Script and storyboard. The script LLM writes the script and storyboard as grammar-constrained JSON (xgrammar), with a script fact check and, on the Islamic plan, quotation verification. The pre-production fee is charged after the price is shown and confirmed (chapter 7).
6. Voice first. The voice-over is generated and locked first (Bangla pronunciation dictionary and text normalisation applied); each scene's length is then set from the audio timing.
7. Key images and preview. FLUX.1-schnell makes key images (or a creator's reference image or a licensed famous-place photo is used); a fast 480p few-step preview is made.
8. Storyboard approval and payment. The storyboard shows the estimated length and full price; "approve & pay" takes the amount from the wallet, and only then does rendering start (chapter 7). The settings version and model versions are stored with the job (10.11).
9. Queue. Scenes are queued with the product label and priority (P50 paid, P10 free) and the delivery tier.
10. Render by scene. Each scene goes to its path: browser (Quick), 2.5D (Enhanced) or Wan 2.2 (Cinematic hero shots on A14B from the approved key image; other scenes on TI2V-5B). Shots are 5 seconds or shorter and stitched with overlap blending. Hero shots get two candidates with automatic best pick where the package or creator enables it.
11. Per-scene checks. Every scene passes frame safety checks, blur and flicker checks, prompt match (OpenCLIP), character consistency (DINOv2), motion and physics defect checks (extra limbs, sliding feet, merging objects), face and hand defect checks, and the scene check (bent buildings, odd food, floating objects). A failed scene is regenerated or repaired (GFPGAN for faces); only that scene is redone.
12. Escalating tiers. For 720p, 1080p and 4K Escalating, the video upscaler runs, Lanczos sets the exact size, close-up faces are lightly restored and the measured quality gate (VMAF round-trip, sharpness, flicker) must pass.
13. Finishing. Colour matching, deflicker and stabilisation across scenes; frame-rate conversion to the ordered rate (25 fps base; 24, 30 and 60 fps selectable); music (ACE-Step or the licensed library) with auto-ducking and beat-synced cuts; mastering to the chosen loudness (YouTube −14 LUFS, broadcast EBU R128 −23 LUFS); captions, titles, logos and Arabic text always added as overlays at final resolution (libass with HarfBuzz shaping); extra aspect ratios by auto-reframe.
14. Lip-sync check. Quick-mode lip-sync is checked automatically; Cinematic close-up dialogue uses Wan2.2-S2V-14B only after its licence check and quality gate.
15. Compile, label and sign. The final MP4 is compiled and validated on the executing GPU node's local SSD; cloned-voice audio carries the AudioSeal watermark; the invisible re-upload watermark is embedded; the Content Credentials (C2PA) manifest is embedded and its hash signed by the remote-signing service, whose key never leaves OpenBao.
16. Store and deliver. The signed file is uploaded to R2 and its checksum verified; the 360p WhatsApp copy, AV1 viewing copy and any ProRes master, SRT/VTT or FCPXML/EDL exports are made (ProRes and timelines on CPU only).
17. Clean up and settle. Only the exact task-owned local files are deleted after verified upload; the job is settled (shorter video → difference back to the wallet; up to 10% longer → no extra charge; failure or late delivery → automatic refund, chapter 7).

### 10.3.1 Job states

| State | Required behaviour |
|---|---|
| Requested / validated | Identity, plan, policy, quota and payload checked |
| Paid / reserved | Wallet charge or free allowance recorded atomically before GPU work |
| Queued | Priority, enqueue time, attempts, job ID and product owner stored |
| Processing | Current scene, progress, node, heartbeat and retry count tracked; checkpoint after every scene |
| Awaiting review | Islamic or safety human review; no GPU reserved and no charge taken until approved |
| Compiled | Final MP4 made locally; format, size and duration verified |
| Uploaded | Stored in R2; checksum and durable acknowledgement verified |
| Completed | Final file reference, settlement and access policy stored |
| Failed / retryable | Drafts and finished scenes kept; refund or retry by explicit rule |
| Cleanup complete | Only task-owned files deleted; cleanup event recorded |

## 10.4 Browser-first execution and device tiers

Render modes are described in chapter 3. This section covers where the work runs.

| Runs in the creator's browser | Stays on RemonLogic servers |
|---|---|
| Quick-mode render (2D/3D animation, motion graphics) with Revideo and Three.js (WebGPU, WebGL2 fallback) | Cinematic video (Wan 2.2) |
| Enhanced (2.5D) motion and render from server-made key images and depth maps | FLUX key images, depth maps and character LoRA |
| Quick-mode lip-sync (Rhubarb mouth shapes, audio-based, works for Bangla and Urdu) | Script and storyboard LLM |
| In-house VITS voices for standard narration and characters | Cloned voices, Chatterbox, Indic Parler-TTS and dubbing |
| Captions, logos, Brand Kit, thumbnail text; audio mixing and loudness (Web Audio) | Safety checks, quality gate and C2PA signing |
| Auto-reframe and Shorts scene detection; preview upscaling and product background removal on strong devices | Server takeover of unfinished browser renders |
| Final MP4 assembly for Quick and Enhanced (WebCodecs + Mediabunny); uploads straight to R2 | Final NVENC encode so browser and server parts look identical |

Device tiers:

| Tier | Devices | What runs where |
|---|---|---|
| Full | Android 10 or later with at least 4 GB RAM, recent Chrome or Edge, laptops and desktops | Every browser feature |
| Light | Android phones with 3 GB RAM; Safari and iPhone | Browser features without heavy models; heavier steps on the server when needed |
| Server fallback | Below 3 GB RAM, or a device that fails the 3-second test render (estimated render time above 6× the video length, default) | Rendered on the server from the start, at the same price |

Browser render safety net: each scene or 10-second segment is a resumable chunk saved in the browser's private storage (OPFS/IndexedDB) and uploaded to R2 at once. Frames are drawn in a Web Worker with OffscreenCanvas, so background tabs keep working; the Screen Wake Lock keeps the computer awake while the tab is visible. The studio sends a heartbeat over Centrifugo; if it stops for 30 minutes (admin setting) the server renders the remaining chunks from the last one backwards while a returning browser continues forwards, and the first finished copy of each chunk is kept. Server fallback uses the same renderer (Revideo in headless Chromium through Puppeteer): 2D on spare Core-1/Core-2 CPU, 3D on idle Rec-node GPUs. Browser-made chunks are treated like uploads: frame safety checks, voice-to-script comparison and one server-rendered check frame per chunk (SSIM) before signing; a failing chunk is re-rendered on the server. A browser render that fails repeatedly moves to the server automatically.

## 10.6 Shared GPU pool, priority and isolation

All GPU servers in the ecosystem work as one pool in one Kubernetes cluster. Any idle GPU takes the highest-priority eligible work, and each pool's owner always comes first.

| Priority class | Work | Rule |
|---|---|---|
| REC | Live-class recording on the recording nodes | Pre-empts everything on those nodes |
| P100 | NexaTute real-time LLM, speech fallback and the safety model | Protected lane |
| P70 | Real-time work borrowed from another product's pool | Always below the owner's P100 |
| P50 | Motion Studio paid script LLM, voice-over and renders (Express first in queue) | Bounded concurrency; ETA shown |
| P10 | Free Trial, Free Beta and internal batch work | Idle capacity only; paused first under load |

- Guaranteed floors on the launch GPU pool: NexaTute 60%, Motion Studio 25%, 15% floating. Motion Studio may borrow idle NexaTute GPUs while NexaTute load is below 50% (normally daytime, when Motion Studio is busiest) and hands them back within one scheduling cycle; at night NexaTute may use idle Motion Studio capacity.
- Pre-emption order: P10 first, then P50 above its floor. Renders checkpoint after every scene, so a pre-empted job resumes without losing finished scenes; LLM answers are never cut mid-response.
- Kueue queues GPU jobs with priority, quotas, cohorts and pre-emption; vLLM priority scheduling orders LLM requests; KEDA scales workers on queue length; the NVIDIA GPU Operator manages drivers and GPU health; the RemonLogic Resource Broker ranks servers by owner, free VRAM, busy share, queue wait and distance.
- VRAM rule: total working memory on any GPU stays under 90%; content-generation models (Wan 2.2, FLUX, ACE-Step) run one at a time per GPU; small models share a GPU through Triton with dynamic batching and NVIDIA MPS (own models only).
- Isolation: separate Celery queues (ms.paid, ms.free), a separate Valkey instance, separate database, roles and credentials, per-product OpenBao secrets, Cilium network policies, and per-product circuit breakers, so an open Motion Studio breaker never blocks NexaTute and the reverse. Prefix and KV caches are never shared across products.
- Data path: scene clips, intermediates and final assembly stay on the local SSD of the GPU node running the job; nothing heavy crosses sites.
- Accounting: every GPU-second and CPU-second is recorded per product by DCGM Exporter, Kueue and OpenCost (chapter 14).

Placement order for Motion Studio work:

| Workload | 1st | 2nd | 3rd | Last resort |
|---|---|---|---|---|
| Script and storyboard LLM (P50) | Main LLM GPU | Other launch GPUs | Idle NexaLogicDev Fast GPU | Hourly cloud GPU |
| Express render (P50, first in queue) | Any free video GPU | Idle Fast GPUs | NexaLogicDev Heavy servers in their lending window | Hourly cloud GPU to keep the shown ETA |
| Normal and Slow renders (P50 / P10) | Heavy servers in the 1–7 am lending window | Idle launch GPUs | Idle Fast GPUs | Cloud only if the 12- or 24-hour window is at risk |
| Free Trial and Free Beta renders (P10) | Idle GPUs only | — | — | Wait in queue; never cloud |

The NexaLogicDev pools join the cluster in 2027 (chapter 17); until then the launch GPU pool and cloud burst are the only paths.

## 10.7 Job queue, checkpoints and failure handling

| Failure | Handling | Charge to the creator |
|---|---|---|
| Worker or GPU node fails mid-render | Node cordoned; job resumes on another node from the last finished scene | None extra |
| Scene fails a quality or safety check | Only that scene is regenerated or repaired; escalated scene re-upscaled with the alternative model, then made at the next native tier if still failing | None extra; escalating price kept |
| Browser render stops | Server takeover after 30 minutes; repeated failure moves the job to the server | Same price |
| Upload of the final file fails | Local file kept; upload retried; job not marked complete until the checksum is verified | None |
| Render cannot finish | Bounded retries with back-off, then dead-letter queue and alert; drafts kept | Automatic wallet refund |
| Delivery late | Express surcharge refunded if more than 20% later than the ETA shown; Normal/Slow later than 12/24 hours get credit (chapter 7) | Refund or credit as stated |
| Duplicate request or retry | Idempotency key returns the existing job | Never charged twice |

Bounded retries, exponential back-off, per-provider timeouts and circuit breakers prevent retry storms. A stuck-job monitor (no heartbeat for a set time, default set from the benchmark) raises an alert on the admin render queue (chapter 13).

## 10.8 Capacity, degradation ladder and festival guard

Planning estimates on the baseline launch fleet (before the GPU test; from the Master Blueprint capacity model):

| Measure | Estimate | Limit set by |
|---|---|---|
| Creators active in the studio at once (Motion Studio alone) | ≈4,500–6,000 with suffix decoding and the compact storyboard schema | Script LLM |
| Cinematic video minutes a day | ≈1,000–1,600 with LightX2V, FastWan and Wan2.2-S2V once benchmarked | Video GPUs |
| Quick/Enhanced video minutes a day | ≈3,000–4,500 | Hero-shot GPU time |
| Free Beta admission | ≈2,000 combined users at once, then at most 70% of measured capacity | Admission cap (chapter 8) |

Degradation ladder (Motion Studio column; levels are shared with NexaTute and switch automatically):

| Level | Trigger | Motion Studio behaviour |
|---|---|---|
| L0 Normal | All pools healthy | Full service |
| L1 Pressure | Pool use above 80% or queue wait rising | Free (P10) jobs paused; paid continue |
| L2 High load | NexaTute real-time queue wait above target | Paid jobs held to the 25% floor with ETA shown; hourly GPU burst for paid renders |
| L3 Overload | Local and burst capacity saturated | New renders paused; scripts, editing and drafts stay available |
| L4 Protect | Error budget breached or all compute down | "The server is very busy right now. Please try again after some time."; read-only studio; queued jobs resume automatically |

Further load controls:

- 1080p Native load pause: when GPU load passes the admin threshold (default 80%), 1080p Native is paused for new orders and 1080p Escalating is offered; it returns automatically.
- Delivery tiers spread load: Normal and Slow orders fill quieter hours and the night window; Slow orders and catalogue or content-calendar batches run at night.
- Festival guard (approved 29 October 2026): before Eid, Pohela Boishakh, 21 February, 16 December and similar peaks, an early-order discount encourages orders before the rush (amount set in the admin, to confirm), and a capacity limit per day and per delivery tier stops the queue from growing beyond what can be delivered on time. When the limit is reached, Express shows a later calculated ETA or "full for today", and Normal and Slow accept orders for the next free window. No scarcity or countdown wording is used.
- Ordering rule for new hardware: a new GPU server is ordered at 60% sustained pool load and brought into service at 80%; hourly cloud GPUs cover the gap.

## 10.9 Cloud GPU emergency burst

- Use: when the GPU site is down, or when paid Express or Normal ETAs would slip, Motion Studio paid renders move to rented hourly cloud GPUs in the USA (spot or preemptible first, on-demand as fallback), using the same signed container images and model versions.
- Creators affected see a new ETA; jobs resume from their last finished scene.
- Spending cap: a monthly cap per product, with alerts at 80% and a stop at 100% (values set in the admin panel, to confirm); every burst hour is charged directly to Motion Studio (chapter 14).
- Never: Free Trial and Free Beta work, minors' raw media and any work that requires data to leave the agreed regions.
- Cloud LLM fallback (text only, for the script LLM under overload) follows the ecosystem order with personal data removed and its own spend cap; speech, video and recording never use cloud LLM APIs.

## 10.11 Model versions, quarterly benchmark and quality panel

- Version pinning: every project records the model versions it started with (video, image, voice, LoRA, safety policy) and stays on them until it is finished, so later scenes match earlier ones. Old versions stay available until no open project uses them.
- Model registry: each model has an exact ID, version, weight hash, licence record, owner and quality-gate result.
- Quarterly benchmark: every quarter new open video, image and voice models are tested on a fixed Bangladesh test set (people, dress, scenery, Bangla text overlays, Islamic scenes, lip-sync) for quality, GPU-minutes per output minute and licence. A model that wins can be switched on from the admin panel (chapter 13) with two-person approval; the switch applies to new projects only.
- Blind viewer panel: before a big model or pipeline update, a panel of Bangladeshi viewers rates old and new outputs without knowing which is which, including emotion quality; the update goes live only if it is not worse.
- Rollback: any model switch can be rolled back with approval; the change is logged as a model-behaviour change.

## 10.12 Software supply chain and licence control

- Only free, open-source software and model weights that allow commercial use are used for self-hosted components. Licences are recorded as SPDX identifiers in the unified software register, with product (Motion Studio, NexaTute or both), placement, version and owner.
- Every release produces an SBOM (CycloneDX or SPDX, by Syft), is scanned for vulnerabilities (Grype, Trivy) and licences (ScanCode Toolkit) in Forgejo CI, and is blocked if any component has an unknown, restrictive or changed licence. The licence process follows OpenChain (ISO/IEC 5230).
- Dependency rule: each component's own runtime dependencies (databases, brokers, bundled libraries, weights) are checked against the same policy.
- Copyleft conditions: LGPL libraries run as separate processes or dynamic libraries (for example Chromaprint); FFmpeg is built without GPL encoders; GPL tools such as Forgejo are used unmodified and are not shipped to customers.
- Deliberate exceptions (paid or proprietary, listed in the register): NVIDIA drivers, CUDA, NVENC and MPS; Cloudflare (CDN, R2, WAF, Waiting Room); the managed transactional email service; WhatsApp Business API and platform APIs (YouTube, Meta, TikTok); payment gateways; the cloud LLM fallback; the C2PA signing certificate.
- Images and model weights are signed, pulled from the Harbor mirror or R2, and kept on each GPU node's local disk, so a borrowed GPU can start serving in about 30–90 seconds.
- Server software updates are never automatic: every update needs two-person approval in the admin panel, goes through staging with automatic tests, rolls out node by node and rolls back automatically if a health check fails (chapter 13).
