## How X16 is built (what I found)

- The page has FOUR areas (`area` state: `q` Content quality, `tm` Tests & marking, `m` Money, `log` Approvals & log) each with a tab key (`qTab`, `tmTab`, `mTab`, `lTab`); the tab list is `TABS` in `renderVals0` and the deep-link hash lists are `HQ/HT/HM` in `st()`. The sidebar sub-list of the "Quality" entry is `mn.subs` = the four areas.
- The location hash `#<tab>` is read once in `st()` (it also sets the area); there was no `#<tab>/<sub>` before.
- Text: 13 `ui*` methods (`uiText` 336 KB, `uiXa` 171 KB, `uiF11`, `uiF7`, `uiTm`, `uiF14`, `uiF16`, `uiAdd17`, `uiBell`, `uiMenu`, …), one literal per language each, merged into one tree `t` (e.g. `uiXa` fills `t.xa`, `t.tabs`, `t.roles.sec`; `uiTm` fills `t.tm`, `t.tabs`, `t.areas.tm`, `t.lg_f.tm`; `uiF7` fills `t.f7`, `t.tabs`, `t.lw`, `t.ad.anyc`, …).
- ONE state, one `act()` (state + activity log + toast), one approvals engine (`apState/approve/reject/effects`) that serves the money, MindForge, Tests & marking and Exam rules sections together, one activity-log renderer (`logWhat`) that reads every section's log lines.
- `renderVals0` is one function with 631 top-level `var` declarations and 28 mutation statements, then one big `return {…}`.

## The method (scripts: `run.sh` = stage1 → stage25 → stage2 → stage3; re-runnable)

1. `stage1.js` — structural cut. Template ranges deleted by line (each range asserted to start at the expected marker and to end at a blank line): X16 loses 1015–2060 (MindForge, Money, Tests & marking, Exam rules); X16b keeps 1015–1626 and loses 573–1014 (content-quality tabs), 1627–2060 (Exam rules) and 2061–2152 (Any-course, Approvals, Log); X16c keeps 1627–2060 only. Then, identical in the three boards: helper methods `secFiles/secMap/secSelf/secDef/secHref/secGo` (secMap = which board holds which tab, one table, identical in all three), the sidebar sub-list (`<button>` for an area that has tabs here, `<a href>` for an area that lives elsewhere), the tab bar (`<button role="tab">` for own tabs, `<a role="tab" href>` for tabs of another board) and the group switch (`xg`), the default area/tab (X16: Content quality › Answer cache; X16b: Content quality › MindForge items; X16c: Tests & marking › Exam recovery), the hash lists (`HQ/HT/HM` filtered to own tabs), `#circ/ps` and `#mf/<sub>` sub-routes, `#ap`/`#log`, load-time redirect for an old hash of a moved tab, bell items whose tab is elsewhere (open the other board), persona buttons (open the other board when their tab is elsewhere), `menuVals` pass-through of `href/isLink/isBtn`, area badge counts (an area's count is shown only on the board that can compute it), title and `$preview` label, a CSS block for the link variants (`.seg a`, `.xa-grp a`, `.dv-m .seg a`) — the only helmet difference from the original.
2. `stage25.js` — settings-kit cards. The `k17run(…,[SPEC])` array has three cards; `tlang`+`pbrev` (template at orig 684–706) stay on X16, `tie` (Tests & marking, 1458) goes to X16b. X16c has none. Whole array elements cut as text.
3. `stage2.js` — code pruning with acorn, three rules: (a) properties of the big `return {…}` of `renderVals0` that only the removed template blocks read (scope-aware: sc-for variables and `r.xxx` reads from other methods are excluded) and the test-hook props `_vat _vatOut _vatCr _ck _po _k _mf` (read by nothing in the repo; dropped where they would keep a moved section alive); (b) top-level `var` declarations of `renderVals0` that nothing live uses (liveness from the kept return props and root statements, mutation statements `x.push/forEach(...)` of a dead variable go with it; free-variable names inside inner functions are excluded); (c) private helper methods nobody calls (`h16v h16Log f11Vals f11Log` on X16b/X16c). Output list: `removed_vals_{a,b,c}.txt`. `undef.js` (free-variable check on every method) reports `{}` for all three boards.
4. `stage3.js` — text pruning per key, identical to the pilot (static usage analysis `usage.js`, per-method mount table, whole-object ranges, a method whose literals are all deleted is removed with its call; the merged text tree is rebuilt from the new file and compared leaf by leaf with the old one: every remaining leaf byte-identical, every removed leaf was "deletable", the removed set identical in all 6 languages). Result: `bad: []`, `langsEqual: true` for all three. Mount table is in the script (e.g. `uiXa:X → xa`, `tabs`, `roles.sec`; `uiF7:F → f7, tabs, lw, ad.anyc, k_mdef, tip.k_margin, ntf.sub/tip`; `uiTm:A2`). Fixes to the pilot's `usage.js`: a bare `t` inside an inner function whose parent declared `t` as a parameter no longer hides it, and `otpVals` reads `r.t` like `menuVals`.
5. Removed: X16 1,114 text leaves (xa 421 of 497, tm 192 of 251, mf 162 of 194, …) , X16b 1,329, X16c 1,709 (per language; same set in all 6). Methods `uiF16` and `uiF14` (hub circular reader texts) are removed entirely from X16b and X16c with their calls.

## Doubts / things I was unsure about

1. **State is per board** (as in the X14 pilot). Approvals, activity log, clock, settings and sample data live in each page's own state. A discount/gift/payout/marking-scheme change proposed on X16b is NOT in X16's "Approvals & log" (the activity-log and approvals tabs are on X16 only) and vice versa; the `Approvals that belong to this tab` card on each money/marking/exam tab still works on its own board because it reads the same approvals engine. The prototype never shared state between boards; links lose state. The 4 initial approvals (a1 institution discount, a2 referral, a4 KPI, a5 MindForge set) and the initial log rows are identical in all three boards, so X16's Approvals list still shows items whose approve button works in X16, but the effect (e.g. the discount going live) appears on X16, not on the money tab of X16b. The lead should decide: either accept (like X14) or move "Approvals & log" so each board shows the approvals of its own tabs only. I did not cut sample data (rule: keep when unsure).
2. **`any-course valuation` in a Money-area slot.** It belongs to the area `m` (tab list `TABS.m`) but is placed on X16. The area button "Money" on X16 then shows one tab; the money area's default tab on X16 is `anyc`.
3. **`$preview` / title of X16** changed from "Prototype: content quality and money" (it no longer holds the money tabs) to "X16 · Quality — Content review, teacher check, translations, approvals and log". The Bengali `<title>` of the canvas entry is in `canvas.json` (not touched; see EXTERNAL_LINKS_TO_UPDATE.md).
4. **Group switch label.** `t.xa.grp.mk` ("Marking & checking") and `t.xa.grp.ex` are kept on X16b and X16c; both switch buttons are shown (one is a link). X16c keeps `t.tm.*` only where `xa` code reads it (28 leaves); the group-switch count badge of the marking tabs (tmMine) is only on X16b.
5. **Test hooks `_vat, _vatOut, …, _mf`** in the vals object were dropped on X16 and X16c (the removed money/MindForge code is their only reader; no file in the repo reads them; `grep` over `prototype/` finds them only in X16 and X12). They are kept on X16b.
6. **Kept although deletable** (shared feed, rule "keep when unsure"): X16 38 leaves, X16b 30, X16c 28 — source copies such as `f7.tabs.*`, `xa.tabs.*`, `tm.tabs.*` that feed both the area-specific object and the shared `t.tabs`, plus `lg`-style shared feeds. Listed in `stage3_{a,b,c}.json` (`kbd`).
7. **Static analysis limits.** `usage.js` follows aliases and member chains; a text object passed whole to a function is treated as root use (the `bare t passed` warnings: `bellVals/otp` `t`, the tooltip helper, `f11Log/h16Log` on X16). The dynamic sweep is the second safety net, but only for the states it lists.
8. `dcverify.py` parity covers `uiText()` only; the side methods keep parity by construction (same keys removed in the 6 languages, checked in `stage3.js`). The 4 new languages are not in the board yet.
9. **Not tested in a real browser** (Design canvas): `<a href>` between `.dc.html` files and the `location.href` redirect. Node only. Link tags in the tab bar carry `role="tab"` and `aria-selected="false"` (they are navigation links in a `role="tablist"`); if the lead prefers a plain nav list the bar can be changed later.
10. **Wording that may conflict with newer decisions (NOT changed; for the lead).** Wallet / stored value / gift cards / discount rates, all on X16b (full list with paths: `wallet.txt`, produced by `wallet.js` over the original English text):
    - Gift cards (`tabs.gift`, the whole "Gift cards (Shikkha Salami)" section: batches with `Made / Sold / Redeemed / Expired`, `g_pol` = "Valid 12 months from sale · unique code on every card · can be given to someone else · no cash refund · VAT charged at sale, not at redemption · retailers keep about 5%", `g_pv` ("valid 12 months from each sale", "NexaTute keeps", "Retailer commission"), `rk.gift` "Shikkha Salami card", `rr.gift`, `rcx.gift` "Gift cards are never refunded as cash", `lw.ref_tr` "Gift card: transfer offered to X instead of cash", `tri.t5` "Refund policy page — gift cards", `pg.ret` "Gift-card retailer", `tip.g_vat`, `ad.gift`, `lw.gift_new`, `lw.gift_live`) — a gift card is stored value with an expiry and retailer commission; check against "no stored money/credits since 30 Oct 2026".
